# Priority 2 decision criteria, v3 (written 2026-11-06)

Supersedes [P2_DECISION_CRITERIA_v2.md](P2_DECISION_CRITERIA_v2.md), which stays unchanged.
Written before any live run of M1, M2, M3 or M4 on the consolidated code. Do not edit this file
after the first live run; a later change needs a v4.

## Reason for v3

The M4 instrument (`gold_m4.py`, `run_gold_m4.py`, `reports_gold/M4_CASES_v1.json`) runs every
ZeroSugar group C case with and without its line. That is the only reading that makes the v1
rule ("keep only if the failure it prevents is otherwise mishandled") checkable. v2 still
describes another design: about 10 calls per profile, a "repair loop" that a single review cannot
show, no rule for a line whose with-line arm also fails, and an M4-O1 condition 1 that ignores
the two team questions the B6 candidate already has. The criteria that decide the study must
describe the instrument that produces the evidence.

## What changes from v2

| Item | v2 | v3 |
|---|---|---|
| ZeroSugar group C test | "Otherwise mishandled", design not stated | Each case runs once with the line and once without it, per profile |
| Mishandled | A false objection, a repair loop, or a false "data absent" claim | A false objection or a false "data absent" claim about the case's point; "repair loop" removed |
| Both arms mishandle, or neither | Not defined | Decision table below |
| Protocol failure in M4 | Stops the whole measurement (v1) | Stops that line only; the line reverts (no evidence) |
| Arm order | Not defined | apinex_test runs "with" first; apinex_gemini_test runs "without" first |
| M4-O1 condition 1 | A validation or information-gathering step | The same, and it does not repeat the two team questions already in B6 |
| M4-O1 condition 5 | Adjudicated, with the block diff as aid | Adjudicated; the missing-line list is a diagnostic aid only |
| M4 cost | About 10 calls per profile | 8 runs, 14-76 model calls per profile |

Everything else in v2 applies unchanged: code under evaluation (`a76b30f`), return point
(`3f9ccb7`), baselines, the v1 stop condition for M1, M2 and M3, the M1 rule for group A, the M2
rule for the two group B lines, the M3 hard cases, the M4-O1 harness, candidate, correction,
repeats and keep rule, and "if M4 is not run, revert all four group C lines".

## M4: ZeroSugar group C lines

### Cases and arms

| Case | Line under test | Point of the case |
|---|---|---|
| C1 | An answer that explains requested evidence is unavailable satisfies the request | The answer says the requested neutral excerpt is unavailable (0 neutral comments) |
| C2 | `task_outcomes`: a declined or failed task is not evidence that data is absent | A Cherry task was declined as out of role; survey ratings exist but were not requested |
| C3 | `CHART_NOTE` | A correct chart: percent of responses, Responses as denominator, no causal claim |

The cases are in `reports_gold/M4_CASES_v1.json`, frozen by `M4_SHA256` in `gold_m4.py` before
the first live run. The "with" arm uses the prompt as committed. The "without" arm removes the
exact text listed in `gold_m4.LINES` at run time (C3 blanks the whole `CHART_NOTE`). The runner
refuses a case whose text is not found once in the prompt, and records `prompt_sha256` of the
prompt constant on every run, as proof of which prompt each arm used.

Each arm runs once per profile (n=1). apinex_test runs "with" first in each case;
apinex_gemini_test runs with `--without-first`, which halves any order effect.

### Mishandled

A run mishandles its case when, about the case's point, ZeroSugar raises a false objection (an
issue, correction or withheld finding that treats the point as a defect) or claims that data is
absent. Each run is adjudicated yes or no on the M4 sheet. A repair loop cannot be observed in a
single review; it shows only as a protocol failure.

A run that ends in a protocol failure is diagnosed first and is not evidence for or against its
line. It stops the evaluation of that line only (the other lines continue), and the line
reverts, because keeping it requires evidence.

### Decision per line

| Without the line | With the line | Decision |
|---|---|---|
| Mishandled | Handled correctly | Keep, only if this holds on both profiles |
| Mishandled | Mishandled | Revert, and record the case as an open defect: the line does not fix what it claims to fix |
| Handled correctly | Handled correctly | Revert: no observed failure justifies the line |
| Handled correctly | Mishandled | Revert: the line makes the case worse |

With n=1 per arm, "holds on both profiles" means four consistent observations: without
mishandled and with handled correctly on apinex_test, and the same on apinex_gemini_test. Any
other combination reverts the line. This is the conservative rule, and the only one compatible
with the principle that no prompt line is kept without an observed failure.

### Cost

8 runs per profile: C1-C3 x 2 arms, and M4-O1 x 2 repeats. At least 14 model calls (two per
review, one per repair) and at most 76 (6 reviews x 8 + 2 repairs x 14) per profile.

## M4-O1: Original validation line

As in v2, with two changes to the pass table.

| # | Condition | How it is checked |
|---|---|---|
| 1 | The added proposal is a validation or information-gathering step (for example, asking the team whether support work is missed more widely), not a direct fix presented as settled, and it does not repeat either team question already in B6 ("Which kinds of support work are most often missed…", "What would keep recognition consistent…"). A duplicate fails: one idea per item | Adjudicated |
| 2 | The added proposal's `citation_ids` include CMT27501 or CMT27502, or SENTIMENT1 | Automatic, from the submitted payload (proposals not in the B6 payload) |
| 3 | The benefit is stated as an assumption ("may", "could", "to check whether"), not as a certain outcome | Adjudicated |
| 4 | No invented cause: the answer gives no reason for why the negative count is small or why support work is left out | Adjudicated |
| 5 | No content lost from the B6 candidate | Adjudicated; the sheet lists candidate lines not found verbatim in the answer, as a diagnostic aid only |
| 6 | No protocol failure (the v1 stop condition applies) | Automatic |

Base rate. The action removed from B6 to build this case was a concrete fix, so the most likely
result is that Original proposes a fix again. That fails condition 1 legitimately and reverts the
line. It is not a harness defect.
