# Addendum D - Runs 46-48, the delivery stall and the safety gate

This file continues [AUDIT_2026-10-30.md](AUDIT_2026-10-30.md) without editing it, and its
sections are numbered D.x to follow Addendum C. It audits the two live workflows that
followed it, Gemini 48 and Luna 47, checks what the delivery record says about 46, 47 and 48,
and files the observations that the per-draft evidence supports. The observation rows
continue the numbering of Part B and Addenda A-C at 32.

It is a read-only pass: no live model call, no code change, no test execution, no commit.
Every figure comes from the three artifacts, their exchange captures, the per-draft
checkpoints, the manifests and the current source at the hashes those runs recorded.

The separation rule of Part B still applies: a **system defect** is a case where the message
or the mechanism could not produce the correct action; **model behaviour** is a decision that
was available and not taken; **design** is a mechanism doing what it was built to do with an
outcome nobody has decided. Observations are filed one at a time, and no row averages the two
models.

Observations 32 to 35 are one failure chain and should be read together. The validator rejected
four items without naming any of them (33); the model could not see which reference was wrong,
so it moved two references between items and then repaired one of the four (34); and one of the
four items could never have passed because the only source it cited carries no quotable text
(35). The stall rule then ended the run at the third rejection of the same check (32), although
the submissions differed and the attempt budget would have allowed three more turns.

Observations 36 and 38 are the release side of run 48, and observation 47 is the rating
contract behind both runs. The support review judged 11 findings supported on every assertion
and named two with a failing assertion; the run released none, and the artifact reports the
reason as "supported 0". The mechanism is deliberate (`zero_sugar.py:690`), and this is the
first run in the 43-48 record where it decided a release: runs 44, 45 and 47 record a safety
score of 3 in every rating block, and 43 and 46 completed no review. What it fires on is a
rating whose rationale is the letter `R` and which has no corresponding issue, so a reader
cannot tell whether the score reflects a real concern or an unfilled field.

Observations 40 and 41 are the repair loop's two costs in run 47. The protocol rejections cost
three model turns and changed no judgment: each was caused by one duplicated ID. The content
losses removed the classification paragraph, the pattern, the limits, the percentages note and
both team questions at draft 2, and the three illustrative examples at draft 4; every one of
those blocks had already been in an answer that an earlier round had reviewed. Observation 48
is the presentation defect that generated one of the complaints: the renderer appended an
excerpt that the model had already quoted inside its own sentence, because the appended text
is a substring of the quoted span rather than the whole of it.

Observations 42 and 43 are reviewer readings, not content gaps: the scope and the denominator
are both present in the answer and in the supplied context. Observation 44 is different in
kind: the reviewer withheld two findings for claims the finding does not make, which no check
detects. Observation 45 is an identifier namespace collision between drafts. Observation 46 is
the counting rule already recorded in observation 25, now visible on the limitation list as
well as the pending list.

## D.7 The safety gate and the reviewer readings

Run 48's release decision rests on one rating:

| Rating | Score | Rationale | Matching issue in the same review |
| --- | --- | --- | --- |
| Accuracy | 2 | `R` | none |
| Clarity | 2 | `C` | none |
| Completeness | 2 | full sentence about the missing excerpts | the excerpt issue |
| Instruction Following | 2 | `I` | none |
| Relevance | 2 | `R` | none |
| Safety / Appropriateness | 2 | `R` | none |
| Usefulness | 2 | `U` | none |

`zero_sugar.py:690` requires `Safety / Appropriateness == 3` for every finding, and
`original.py:552-554` then withholds the whole set when the score is below 3. A rating whose
rationale is one character and which no issue explains is therefore sufficient to convert 11
supported findings into 0 released. The same one-character pattern appears in every rating
block of both artifacts: in run 48, 3 blocks; in run 47, 9 blocks. Completeness is the only
rating that ever carries a sentence.

Accuracy is read the same way and has a different effect: `zero_sugar.py:1458` forces `revise`
when it is below 3, but it does not withhold a finding. In run 47 accuracy is 2 in six of the
nine blocks while the safety score is 3 in all nine, and the run released five findings. Two
ratings written as a single letter, one blocking acceptance and one blocking release, and
neither is required to say what it observed.

The two reviewers did not apply the same criteria, and the difference is larger than in the
43-45 pair:

- Gemini's completeness review raised one issue, the missing literal excerpts, and did not
  repeat it. Its support review re-raised the same issue as its first of three, with the same
  correction ID prefix, so one obligation was counted by both phases.
- Luna's completeness review raised 3 or 4 issues in every round. The scope complaint appeared
  in 4 of 4 rounds with a new correction ID each time, although `authorized_scope` (M14,
  2026-07-01 to 2026-09-30) and `authorized_teams` were supplied and the instructions say not
  to infer omitted teams from an authorized team name. Round 1 also issued a mandatory
  correction whose own text says the answer provides exactly two questions, which it did.
  `zero_sugar.py:1461-1464` rejects a `revise` verdict that carries no correction, so a
  reviewer that wants to block a compliant answer must attach the block to some obligation;
  the round-1 correction meets that rule by naming an obligation the answer had already met.

Three readings in run 47 are internally inconsistent, and they are worth recording separately
from the scope dispute:

- F11:A2 is assessed `contradicted` with the reason "The phrase 'the two negative comments and
  mixed comments' is internally consistent with the evidence, so the reasoning is sound", while
  the finding-level reason says the premise is supported. The published limitation reproduces
  both halves in one sentence.
- F9:A2 is assessed `insufficient_evidence` and asks that the negative comments be added to a
  proposal's citation basis. The model complied at attempt 3 of the same draft.
- The excerpt requirement moved between rounds: round 1 said no positive excerpt was given,
  round 3 said only the positive one was clearly labelled, round 4 said no literal excerpt
  existed. Only the first and last describe the answer accurately.

F2 and F6 are withheld for assertions that do not appear in the text they review. F2:A2
attributes to F2 the claim that the 13 comments "represent all eligible ... for the full Q3
2026 quarter"; F2's published text says the classification covers the supplied comments. F6:A1
attributes the claim that "Only one team appears ... justifying the absence of suppression";
F6's text asks a question about recognition behaviours. Neither claim is in the block, and no
check compares an assertion to the text it is attached to.

## D.10 Limits of this audit

- Read-only pass over three artifacts, their exchange captures, the per-draft checkpoints, the
  manifests and the current source. No model call, no test run, no code change, no commit.
- Counts are mechanical: calls and events from the captures, findings and release sets from the
  artifacts, characters and token counts from the logged requests, duplication from Jaccard
  overlap with the method stated in D.5.
- No label, citation, correction or claim was graded semantically. Where the answer and the
  review disagree, this file reports both and does not decide which reading of the question is
  right.
- One pair per provider, with generator and reviewer served by the same model in each run. Any
  difference between 47 and 48 can be a provider difference, a reviewer difference, or both.
- Run 48 has one reviewed draft. Its draft table describes one answer and three rejected
  repair submissions, not four reviewed answers, and no completeness or support decision was
  taken on any of the three.
- The `excerpt_source` item count in D.5 is read from the rejected submissions as captured. The
  validator does not report it, so the count is the auditor's, not the system's.
- The 46 network artifact is included for the record only; its capture was read for the
  terminal events, not event by event, so its figures are the artifact's counters.
- Nothing here relaxes the correction-state rule, the evidence-ID rule, the draft cap or the
  attempt cap, and nothing reduces findings, sources or assertions to make an outcome fit.

# Addendum F - Review of the 49-50 remediation plan

The document reviewed here is `planpost49_50.txt`, 41 lines received on 2026-10-31 after
Addendum E: six changes split between Python and the ZeroSugar model, three validation
steps and one success criterion. This addendum checks its premises against the two
artifacts and the source, states where the plan cannot be implemented as written, lists
what it leaves out, and records the decisions it creates. It continues the same file and
does not edit Addenda D or E.

It is an analysis of a document: no item is approved, nothing is implemented, and no live
call, test, code change or commit was made. The plan's numbering is kept so a later reader
can compare the two texts line by line.

The plan's own guardrail is its strongest element and is recorded before the criticism:
if ZeroSugar keeps failing on fixed candidates with complete context, the next change
belongs to its instructions, configuration or model, and loosening Python to accept those
evaluations would not solve the problem. That is the same conclusion as E.10, and it closes
the cheapest wrong turn available.

## F.3 One new observation from this pass

| # | Observation | Evidence | Class | Detail |
| --- | --- | --- | --- | --- |
| 62 | Draft 3 presents a per-comment classification that disagrees with two stored labels, and the completeness phase accepts it with score 3 | `review_history[2]`: candidate `2a921c25e95673d4`, completeness `accept`, `issue_count: 0`; candidate text lists `CMT27512` positive and `CMT27510` mixed; stored labels are mixed and positive respectively | Design plus model behaviour | 2 of 13 labels wrong, with the aggregate 8/2/3 unchanged, so the error is invisible at row level |

Run 49's third draft answers the complaint that Addendum E records: it lists positive
`CMT27500, CMT27503, CMT27504, CMT27505, CMT27506, CMT27507, CMT27509, CMT27512`, negative
`CMT27501, CMT27502`, mixed `CMT27508, CMT27510, CMT27511`. The stored labels put `27510`
in positive and `27512` in mixed. The writer did not have either label: it inferred both
from the six examples and from the comment text, and the swap preserved the counts.

This completes E.3 rather than contradicting it. E.3 records that the third completeness
call accepted the third draft; row 62 records what that acceptance covered. The completeness
reviewer receives no labels and no evidence by design, so it could not have caught the swap,
and the support phase that could receive them never produced a verdict. Item 1 of the plan
is therefore necessary, and by itself not sufficient: delivery fixes the input, not the
rendering.

One property of the stored label record matters for how item 1 is implemented. Its `quote`
is a supporting fragment of the comment, not the comment: all 13 are literal substrings, but
only 10 are prefixes, and `CMT27501`'s is its first sentence while the full text has three.
Sending the labels with that field unlabelled would invite the writer to present an excerpt
as the whole comment, which is the class of error Addendum D already files at 41.

## F.4 Where the plan is not implementable as written

**Item 3 says "within the existing budget" and the evidence says the binding limit was
something else.** Neither run exhausted the shared budget at the point of failure: run 50
stopped with 19 calls and 659.91 s left because `MAX_REVIEW_ATTEMPTS` is 3 and three
attempts had been spent on two-call turns. Normalising equivalent duplicates is a code-side
change with no model turn. Requesting one consolidated evaluation costs a turn, and in run
50 there was no fourth turn to spend. The plan therefore needs one of three statements it
does not contain: count the consolidation request outside the attempt cap, define the
terminal state reached when the cap is hit, or allow the first call when another call
declares itself accidental, which is what run 50's second call did in its own rationale. The
plan explicitly refuses automatic first-call selection as a general rule, which is
defensible; it cannot refuse it and also rely on a turn that does not exist.

**Item 3's "keep the independently validable parts" is per-item validation, not salvage.**
A review submission is atomic: decision, score, rationale and corrections arrive together,
and corrections without a decision release nothing. Run 49 makes the scale concrete: the
model resubmitted 19,545, 19,879 and 19,885 characters three times, and the last attempt
differed from the second only in `correction_judgments`. Localised repair is the right goal;
the plan should describe it as validating each item and re-asking only for the failing one,
which is a larger change than the sentence suggests.

**Item 3's diagnosis of run 49 stops one step short.** A better message with the item index
and the colliding index would have told the model what it already knew: the enum offered
`C_d523d22a387e704b_visible_1`, `C_a51013e9d2d475bf_F9_assertions` and
`C_a51013e9d2d475bf_F10_assertions` for two obligations that both belonged to the F10
assertion. The only remaining move was `null`, which drops the refinement. The fix is an
identity change (a distinct obligation ID per defect, or reconciliation before validation),
not a feedback change, and the plan places it under "recovery" where it will be implemented
as a message.

**Item 5 has no mechanism and no terminal state.** The plan is right that a defective
explanation should not send the writer to change the answer, and right that a length rule
would not do. It does not say how to tell an explanation defect from a substantive objection
when both arrive in one report. Run 49's second support round carried three corrections and
one-character rationales in every rating; a rule that routes defective-explanation reports
back to ZeroSugar without separating them would discard the three corrections. It also does
not say what happens if ZeroSugar repeats the letter within its three attempts: no review,
a partial release of the previous candidate, or a failure. Those are three different manager
outcomes.

**Item 5's "not a length rule" needs a replacement criterion.** If a long explanation can
also be wrong, the implementable minimum is structural: name the dimension, name the
evidence consulted and name the specific gap. That is checkable in code without judging
meaning, and the plan should say so, or item 5 has no acceptance test.

**Item 4's first half is close to a no-op.** The stable input already exists and the prompt
already requires a location. The increment is turning that guidance into fields. The plan
presents both halves as new work, which would overstate what the change delivers.

## F.5 What the plan omits

1. **A deterministic check that the rendered labels match the stored ones.** This is the
   cheapest guarantee of the plan's own first objective and the only one row 62 shows is
   missing. Python holds both sides: the 13 stored labels and the rendered classification.
   No model call is needed to compare them.
2. **Thresholds and a fixture set.** "Evaluable explanations" and "no false objections in
   the checked cases" are not measurable without a labelled set and a rate. The plan gives
   neither a baseline nor a pass mark.
3. **Contract versioning.** Adding labels to the evidence and fields to the review changes
   the payload identity that checkpoints and replay depend on. The project's rule is that
   saved versions keep their semantics, so the plan needs a review version and an evidence
   version decision before implementation, not after.
4. **Cost accounting.** The extra turn in item 3 and the richer input in item 4 add to
   requests already measured at 17,801 to 37,504 input tokens per review call. "Consumes
   the existing budget" is not a number.
5. **An acceptance policy.** Both runs failed administratively, not analytically, and the
   partial release already worked: 10 findings released, 4 withheld. The plan improves the
   machinery but does not answer the business question it exposes, which is what is
   published when a review is valid but the answer is imperfect, and who accepts that.

## F.6 The three validation steps

The order is right: contracts first, the reviewer in isolation second, the full workflow
last. Two corrections to how they are described.

The first step can do more than the plan claims. The stored artifacts contain a candidate
whose labels are independently checkable, which is draft 3, so the label comparison of F.5
can be built and run offline against a real fixture rather than a constructed one. What the
first step cannot show is that the writer would have rendered correctly had it received the
labels; that is what the third step measures.

The second step needs something that does not exist yet: a fixed set of candidates with
known defects and known good passages. Without it, "no false objections in the checked
cases" cannot be evaluated, and the success criterion stays unfalsifiable.

## F.8 Limits of this review

- It reviews a document. No item was implemented, so no effect was measured and no estimate
  of improvement is offered.
- Premises were checked only where an artifact or the source can show them. The claim that
  ZeroSugar objects to content that is present rests on one arguable case in run 49, the
  second-round request for an explicit quarterly denominator, which the phase prompt already
  excludes as a requirement. That is one case, not a rate.
- Row 62's label comparison is string equality against the stored labels. It grades the
  mapping, not whether the classifier's labels are right, and it does not reopen the
  semantic questions Addendum E leaves open.
- The observation numbering continues E's table at 62. No row averages the two runs, and
  nothing here reclassifies an existing row.
- Character and token figures are the ones already logged; the review adds no new
  measurement of its own.
- Nothing here approves an item of the plan, relaxes a gate, or changes the attempt cap,
  the draft cap or the release rule.
