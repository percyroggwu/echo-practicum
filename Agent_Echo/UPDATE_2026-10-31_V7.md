## Implemented changes

- New sentiment reports identify source-facts-v7. Privacy-released classifications
  carry every comment ID, stored label and source hash, bound to scope and rubric.
  Suppressed groups supply no classification records. Legacy reports without the
  marker produce their old summary exactly.
- Original receives the full released map. The canonical per-comment table is built
  from these records and retained in its source-bound selection. Reproduction checks
  compare the rendered table, source hashes, record identity and aggregates. Swapping
  two labels without changing category totals fails replay. Support review still checks
  the evidence against the retained specialist report; the binding is not a semantic
  sentiment certificate. Arbitrary contradictory narrative still requires model review.
- Proposal quote_ref is null-only, matching the renderer. Examples use interpretations
  and their individual textual source IDs. All prior quote/source controls remain.
- Correction duplicate feedback includes the exact obligation and conflicting indices.
  Independently valid finding entries can be cached before link parsing for localized
  repair. No invalid/partial review authorizes release. F9 and F10 were both offered in
  run 49; no automatic merge or assumption of a forced collision is implemented.
- Review phases have three ordinary attempts. One additional protocol attempt is shared
  across the whole workflow, only after conflicting calls or correction identity errors
  persist at the ordinary limit and global model/tool/time headroom remains. It consumes
  the existing shared budget. It is not available for semantic disagreement, truncation
  or explanation repair. Equivalent parsed calls may be normalized without a model call;
  competing calls are never selected using their order or their self-description.
- New review-v7 requests scores plus a structured explanation per dimension: dimension,
  existing reference IDs and a concrete observation. The observation becomes the stored
  rationale, avoiding duplicate generated explanations. Python checks shape/references,
  not semantic correctness. One-character/missing explanations cannot certify acceptance.
- After a substantive review validates, explanation-only calls can consume the remaining
  ordinary support attempts. They see the same candidate and frozen scores/corrections;
  they cannot overwrite substantive judgments. On failure those judgments remain, the
  decision requires revision, and supported findings may still qualify for the existing
  partial-release policy. Explanation-only failure does not assign answer rewriting to
  Original. If substantive corrections exist, those corrections retain their owners.
- Exhausted review delivery is categorized review_protocol_error, separate from a model
  judgment that the answer needs revision. Failure text names phase/candidate and makes
  earlier reviewed-candidate release distinct from the unverified newest candidate.
- Request accounting records request characters, elapsed seconds and available provider
  token counters, including explanation repairs. It contains no question/source text.
  Shared snapshots preserve the single-exception counter and accounting across full
  workflow continuation. Missing provider usage is explicitly marked, never estimated
  as measured tokens. Equivalent-call normalization costs no model request.
- Editing instructions request consolidation of repeated explanations/questions without
  lexical similarity gates. Five roles, both independent review phases, privacy/scope,
  safety gating, source controls and four-draft bound remain.

## Contracts and historical behavior

New answers use source-facts-v7; v1-v6 replay remains available. New live reviews use
review-v7, with an optional exported explanation_quality field so saved reviews without

## Evaluation instrument and acceptance

review_cases.py defines nine controlled candidates: a complete answer and individual
count, percentage, denominator, positive/critical example, citation, label-fidelity and
question-audience defects. Their explicit annotations were authored by the coding agent
independently of a model under test, not by an external human sentiment annotator.
evaluate_review_cases.py exports immutable inputs or scores fully annotated reviews;
it never calls an API or labels free-form objections with wording heuristics.

The controlled threshold is zero false-positive objections and zero missed injected
defects across all nine cases. The scorer reports counts, false-positive rate and recall,
with exact corpus identity and reviewer/annotation provenance. Its self-tests validate
the instrument only. Baseline and actual provider performance on this corpus are
unmeasured; do not turn scripted fixture success into model accuracy.

The two authorized live workflows use the same historical M14/Q3 Recognition request,
database, profiles, lexical retrieval, 32-call and 1000-second shared limits and 6000-token
provider output cap. No additional isolated API evaluation is hidden in local checks.
Output quality is assessed from the actual candidates/reviews separately from execution
success. Findings supported by valid reviews may be partially released under existing
controls; complete acceptance requires both phases, objective gates, resolved mandatory
work and complete explanations. A structurally valid explanation may still be incorrect.
