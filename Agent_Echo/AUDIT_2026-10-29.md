# Part B - The separation rule

An audit that files every failure under one label ends up micromanaging the model: each
failure looks like a compliance problem and the remedy is another rule. Runs 39 and 40 do not
support that reading.

> A failure is a **system defect** when the message the model received could not yield the
> correct action, or when the system could not carry a correct answer through its own format
> limits. It is **model behaviour** when the information was present and the decision was
> incoherent. It is **design** when the mechanism does exactly what it was built to do and the
> outcome is a trade-off nobody has decided yet.

The rule is deliberately about what the model could know, not about whether its answer was
right. None of the observations below is a case of the model reaching a defensible conclusion
and being blocked for it, which is why none of them justifies relaxing a judgment rule.

# Part C - P0-6 The repair turn defeats itself in Original

`original.py:713-718`; `runtime.py:220-237,287-303,331-333`.

The repair context is the raw candidate answer as an assistant message plus one JSON object
holding the complete support verdict and the complete evidence. Measured on run 39's failing
call: 68,710 characters of history, of which the four actionable corrections are 2,647. The
serialized verdict alone is 37,081 characters, the evidence appears twice (9,505 inside the
verdict and 9,729 again as the original retrieval message), and the instructions add 35,624.
The call consumed 32,854 input tokens, emitted 18,502 characters of prose with no tool call,
and ended at `finish_reason: length`. Its own text shows the chosen strategy: "remove_ids
includes all 23 old blocks... I'll remove all old blocks and add fresh content", followed by
"does not including a block in reuse_ids drop it, or does the draft persist?". The contract
answers that at `runtime.py:290-291`; the doubt appears anyway inside 35,624 characters of
instructions, and the model resolved it toward a full rebuild.

## No layer recovers

The shared answer loop calls the model without an `OutputTokenLimit` handler
(`runtime.py:331-333`); only the two review phases retry (`zero_sugar.py:998,1233`).
`original.py:399` catches a child specialist's `AgentRunError`, not Original's own truncation.
Run 39 stopped with 23 model calls and 789 seconds unused.

Whether reading a smaller package would have kept the model inside 6,000 output tokens is not
established by this run. The recovery path does not depend on that guess: a truncation handler
plus the compact instruction is verifiable offline, and it is what A19 asks for.

This is also the correction to the 28 audit's P1-5: the fix shipped there covers both review
phases and not Original's answer path, and run 39 failed on exactly that asymmetry.

# Part D - P1-11 and P1-12: the rejection path

## P1-11 Independent structural defects are reported one at a time

`zero_sugar.py:441-450,603-633,1267,1275-1279`.

One submission can break several rules, and every layer surfaces exactly one.
`validate_assertions` raises on the first bad assertion (`:626`), so two assertions carrying
the same duplicated citation cost two attempts. `normalize_finding_submission` already builds
one error per finding and then raises `errors[0]` (`:447`). The support path validates findings
(`:1267`) before the correction-state rule (`:1275`), so a submission holding both kinds of
defect only hears about the first.

Run 40's fourth review is the case. Attempt 1 carried a duplicated citation in
`F10.assertions[0]` and the `C_d1406582a33103e7_visible_2` state conflict; only
`assertion_citations` was reported. The conflict surfaced on attempt 2 and consumed a second
of three attempts. Nothing in the design requires the one-at-a-time order: the list of
findings errors already exists, and the state check could run beside it.

## P1-12 A rejection can name the field without naming the item

`zero_sugar.py:1275-1279`.

`correction_refinement_state` raises with `field="corrections.related_correction_id"` and the
sentence "An active refined correction must have an explicit mandatory, unaddressed judgment
for the same ID". The submission held 9 judgments and 4 linked refinements, and exactly one
pair conflicted; the message identifies neither the pair nor the count. The model responded by
changing the part that was not wrong: the corrections block serialized identically on attempts
2 and 3 (`1a41c42eb091`), and the diagnosis recorded `condition_status: repeated` with the
same `condition_id` (`d41cfcd3fae381c2`). The citation path shows what the alternative looks
like - it returns the field, the received IDs, the allowed IDs and the retained and missing
finding IDs (`:626-628,449`), and in run 40 five such rejections were each fixed on the next
attempt.

part that was not wrong:

# Part F - Run 40 could not have converged

At draft 4 the model judged nine obligations, marked six addressed and left three mandatory
ones unaddressed, and returned `revise`. `MAX_DRAFTS` is 4 (`original.py:22`), and the loop
raises once `attempt + 1 >= MAX_DRAFTS`, so a valid fourth review would have ended the run in
the same `partial` state. Repairing `correction_refinement_state` would have produced a
complete review and the same outcome.

That distinction is the one the 28 audit's revision 6 missed. The contract rejection cost the
evidence of the model's judgment, not the result. Any plan that presents this repair as the
way to a correct output is measuring the wrong thing.

What this also withdraws: revision 6 read Luna 40 as a case of the model contradicting its own
review. The artifact does not support that. The model's judgment was internally consistent -
four linked refinements, one of them closed by its own judgment - and it was the message, not
the judgment, that was unactionable.

# Part H - Plan

The sequence in the 28 audit was written when the review budget was the binding blocker. It is
not: the bounded review completed on its first attempt and nothing truncated. The replacement
sequence separates transport from convergence, and puts a decision gate in front of the only
step that needs one.

| Phase | Work | Gate before the next phase |
| --- | --- | --- |
| 0 | Freeze this diagnosis. No code, no run. | Accepted by the reader reviewing this document. |
| 1 | Define the success criterion (Part I). A decision, not a change. | One sentence in this file stating what a future run must show. |
| 2 | Transport: A19 (Original truncation), A8 (repair package), A18 (named conflict), A17 (batched defects). Offline only. | Focused tests for each, full release gate green, no live call. |
| 3 | One live run per provider, one variable at a time, same case and budget. | Both review phases complete in every draft; the repair turn reports its own input size and whether it truncated. |
| 4 | Convergence: A3/A4, or accept `partial` as the designed outcome. | Explicit decision; no code until then. |
| 5 | A15 accuracy evaluation. | A complete delivery exists to evaluate. |

*Plan status after runs 41/42 (Addendum A, A.11): Phase 2 shipped, Phase 3 ran ahead of
Phase 1, Phase 4 still undecided.*

Phase 1 exists because two different goals are currently called "a correct output": a delivery
that both reviews accept, and a delivery that keeps every finding, source and assertion even
when the verdict is `revise`. The second is a contract property and can be tested offline; the
first depends on the model converging and is not a property of the code. Evaluating the second
first is what makes a failure attributable.

---

# Part I - Decisions this diagnosis cannot make

Three questions are needed before Phase 2 changes anything. None is answerable from the code,
and all three change what Phase 3 is allowed to conclude.

1. **Which target counts as success** for the next live pair: acceptance, or complete delivery
   with full coverage under a `revise` verdict?
2. **Whether the observed `partial` is a defect at all** when both reviews completed, every
   finding is justified and the answer was genuinely incomplete.
3. **How convergence is bounded**: more drafts, fewer new obligations per pass (A4), or an
   explicit decision that an incomplete answer is published as incomplete.

# Part J - What this plan will not repair

- **Model judgment.** No label, chosen citation, assertion assessment or written finding is
  changed or normalized. That needs semantic evaluation, not a patch.
- **The state rule, relaxed so a defective delivery passes.** Dropping the link on an
  obligation the model closed would have accepted a submission the rule exists to stop, and
  run 40 shows it would not have changed the result.
- **Deterministic duplicate detection.** Presentation stays a review judgment. At most the
  author can be *told* that two of its blocks are near-identical, which is information, not a
  gate, and it is not proposed here.
- **Coverage, sources or assertions reduced to make an outcome fit.** P0-6 and P1-11/P1-12
  shorten messages and name items; they remove no judgment and no obligation.

# Part K - Limits of this diagnosis

- It is a read-only pass over runs 39 and 40, their private exchange captures and the current
  source; it ran no model call and changed no code. Its numbers are recomputed from those
  files, not carried over from the 28 audit, and the working tree was checked against
  `reports/review_corrections_manifest_20261029.json` first (0 mismatches).
- The duplicate markers in Part E are a mechanical count of section labels that occur twice in
  the visible answer. They locate a repeated section; they do not judge whether the repetition
  is harmful, which stays a review judgment. The same applies to the "96% non-actionable"
  figure: it is the share of the repair history that is not the corrections, not a claim that
  the rest was useless.
- The two usage counters are reported separately, as the 28 audit's revision 4 says, but their
  values are not mutually consistent in this evidence: the Chat adapter reports
  `reasoning_tokens` almost equal to `output_tokens` on every completed call (run 39: 4,255
  output, 4,254 reasoning), which cannot describe a review of several thousand visible tokens,
  while the truncated call reports 1,374 against 6,000. The counters are therefore not usable
  as arithmetic, and this diagnosis draws no conclusion from them. Revision 4's conclusion -
  that the cap is consumed by the review JSON, since a full review was produced from 3,471
  output - does not depend on that decomposition.

  *Superseded in part (Addendum A, A.10.5): the equality does not hold in every run - 966
  output against 21 reasoning in run 41, 1,725 against 904 in run 40, and one call with
  `None`. The counters remain unusable as arithmetic.*
- "Run 40 could not have converged" is a statement about the submission the model actually
  made at draft 4: nine judgments, three mandatory unaddressed. It is not a prediction that a
  differently-worded contract would have produced the same judgments.
- This document does not evaluate answer quality. It classifies delivery failures and states
  what the model could and could not have known; it is not semantic validation of any finding,
  label or correction.
- Run 39 completed one candidate review and run 40 completed three of four. Neither run
  reached the accuracy question the 28 audit's A15 asks, so nothing here says the delivered
  content is right - only that two specific delivery mechanisms failed and one was fixed.

## A.6 P1-13 The corrections block is validated last, so a first-attempt defect is reported on the last attempt

`zero_sugar.py:709-734,1275-1318`.

The support path validates in three stages: refinement state, findings, then the normalized
report that contains the corrections. A17 merged the first two. The third still raises on its
first offending entry and still runs after `normalize_finding_submission`, so:

- an error in `corrections` is invisible while any finding error remains;
- only its first bad `item_index` is named, even when several are wrong;
- if it first surfaces on attempt 3, the phase fails with the finding judgments already
  retained.

Run 42 is the case. Attempt 1 carried both defects. The first two rejections described only
the citation duplicate, which the model repeated; the third attempt corrected that field and
met the corrections error with no attempt left. A fourth attempt is the cheapest
counterfactual and it is not obviously sufficient, because the same model repeated a fully
specified citation error twice. Reporting both defects at attempt 1 is strictly better than
one more attempt, and it is the same batch A18 already proved usable.

This is not a request to relax the evidence-ID requirement. The rule stays as it is; the
change is when the model is told.

## A.7 P1-14 The corrections citation field never says which ID space it wants

`zero_sugar.py:730-733`, and the `corrections` item in the support schema.

`corrections[].citation_ids` is `{"type": "array", "maxItems": 16, "items": {"type":
"string"}}`: no description, no enum. Its neighbours in the same object are stricter -
`request_ref` is an enum of the supplied question excerpts, `related_correction_id` is a
nullable string. The instruction says "For each NEW problem return one corrections entry with
issue, kind, owner, specific requested_change and existing citation_ids that can help." A
finding ID is an existing citation ID in the submission, and the model used six of them per
correction, consistently, in all three attempts. It did not invent anything.

The rejection returns `field`, `item_index` and one sentence. `assertion_citations` returns
`received_citation_ids`, `allowed_citation_ids`, `missing_finding_ids` and
`retained_finding_ids` (`zero_sugar.py:607-637,449`). The corrections field gets none of that,
so the only way to learn the namespace is to be rejected, and in run 42 the rejection arrived
when no attempt remained.

For contrast, the assertion field is described in the instructions as "the relevant subset of
that finding's citation_ids". The ambiguity is specific to the corrections block.

This does not excuse the model's reading. It says the contract did not exclude it and the
message could not correct it in time. That combination is what makes it a system defect.

## A.12 The fourth decision

The three questions in Part I are unchanged and still unanswered. Run 42 adds a fourth.

1. **Which target counts as success** for a live pair: acceptance, or complete delivery with
   full coverage under `revise`? Run 41 delivered 9 supported findings and was not accepted.
2. **Whether `partial` is a defect** when both reviews completed, every finding is justified
   and the answer is genuinely incomplete. Run 41 is that case with draft 4.
3. **How convergence is bounded**: more drafts, fewer new obligations per pass, or publishing
   an incomplete answer as incomplete. Run 41 used the fourth draft; run 40 could not have
   converged (Part F) and did not.
4. **What a protocol stop releases.** Run 42 judged 13 of 15 findings supported, retained all
   15 structurally, and released nothing because a citation field failed three times. Run 40
   failed the same way at draft 4 and released 12 findings, because an earlier draft had
   completed a review. The difference is not the failure but whether any review completed
   before it: `incomplete()` publishes the last reviewed candidate, so a stop on the first
   draft publishes nothing and a stop on a later draft publishes the previous one. The options
   are to keep that rule, to release the supported findings of the failing submission with the
   partial wrapper, or to publish nothing and report the judged counts in the failure text.
   Any of the three is defensible; the current asymmetry is not a decision anyone made.
