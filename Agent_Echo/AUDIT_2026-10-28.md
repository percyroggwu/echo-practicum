### Revision 3 (same day, second external pass)

- **A1 was wrong again.** A static `12 - retained` cap blocks a legitimate
  remove-one/add-one replacement at full capacity, and the schema cannot see `remove_ids`
  or dedupe. Capacity must be enforced on the resolved list.
- **A3 was underspecified.** Identity has to name the *objection*, not only the claim: two

- **A9 over-corrected.** Owner-based delegation strands an Original-owned correction that

- **Editorial fixes, verified in the logs.** Run 36 recorded **seven** `narrative_count`
  rejections (21, 25, 24, 23, 23, 23, 23, turns 1-7), not six, and the feedback does carry
  `expected_count`/`actual_count`. The `1 -> 4 -> 2 -> 9 -> 11` sequence mixed completeness

  model-quality problem is dropped: the model resubmitted 23 items for four turns after
  being told the limit was 12.

## Headline

The analytical pipeline works; the delivery contract around it does not converge. Two
independent loops were found in code. The answer loop reproduces in run 36; the obligation
mechanism shows in run 35 but did not reproduce in run 36:

1. **The answer loop.** `submit_grounded_answer` submits *additions* that are merged with
   the retained draft, but the merged result is validated against a 12-item cap on the
   merged list that the additions schema never expresses. Run 36 hit it on all seven turns
   and died at the turn limit.
2. **The obligation loop.** Every repair draft can mint new mandatory corrections with a
   new identity, and nothing merges or caps them. Run 35's support phase went 4 -> 9 -> 11
   issues across three drafts, and the next support review failed at the output-token
   limit with those 11 carried into that draft.

Both loops are structural: another instruction paragraph changes the probability, not the
mechanism. Run 36 also shows the model resubmitting 23 items for four turns after being
told the limit was 12, so model compliance contributes. Fixing the contract is necessary
and not sufficient.

## What works and should be preserved

- **Provenance.** Scope, source hashes, citation IDs by finding ID and SHA-256 of every
  code file travel with each artifact.
- **Withholding.** A finding with a failed assertion is withheld as a whole
  (`zero_sugar.py:618-620`), and the safety/deterministic gate withholds everything if
  either fails (`original.py:529-531`). Run 36 released 13 findings and withheld 3.
- **Deterministic vs model split.** SQL replay, source binding, scope, arithmetic and
  privacy are code; meaning is judgment.
- **Containment.** Rejected deliveries never become approvals; retained reviews are
  candidate-bound (`zero_sugar.py:1039-1046`).
- **Experiment discipline.** `echo_review_experiment_20261028/` freezes baseline, inputs,
  budgets and variants and refuses to declare a winner from eight runs.
- **Credential and privacy basics.** `.env` ignored, no secrets in `connections.json`,
  small-group suppression, read-only tools.

# Part 1 - How ZeroSugar actually decides

## 1.1 Two independent phases

- **Completeness** (`zero_sugar.py:890-1001`) sees question, visible answer, scope and
  team names, never evidence. Three attempts.
- **Support** (`_review`, `zero_sugar.py:1030-1314`) sees the full evidence packet, the
  findings, prior obligations and pending numeric requests. Three attempts.

Both phases are re-run for every draft. Nothing is reused across drafts except the
per-candidate finding cache, which is invalidated whenever the answer changes
(`:1039-1043`). That is the correct conservative choice, and it is also the reason cost
scales with drafts.

## 1.2 Five sources of a mandatory correction

An obligation enters the queue from any of these:

| Source | Code |
| --- | --- |
| Model-authored corrections in the submitted review | `:820-837` -> `issues` |
| Every finding with at least one non-`supported` assertion | `:1226-1235` |
| Unresolved prior obligations, re-appended verbatim | `:1259-1269` |
| Completeness omissions merged into support | `:1237-1241` |
| Unretired numeric coverage / incomplete sentiment | `:1248-1258` |

## 1.3 What retires one

Only an explicit per-obligation judgment (`mandatory`, `addressed`) derived in code
(`:776-800`):

- `mandatory=false` -> withdrawn
- `mandatory=true, addressed=true` -> resolved (or withdrawn if it came from this
  draft's completeness phase)
- `mandatory=true, addressed=false` -> unresolved, and it stays

There is no code path that merges two obligations, caps the queue, or retires an
obligation because the underlying finding is now supported. Retirement is entirely model
judgment, on keys the model did not choose.

## 1.4 Why the queue grows instead of shrinking

Four mechanisms, all in code:

1. **Correction identity is candidate-and-content derived.** A support correction is
   keyed `C_{hash(answer + issue)}_support_{n}` (`:1211`); assertion corrections are keyed
   `C_{hash(answer)}_{finding_id}_assertions` (`:1232`); completeness corrections are keyed
   with the answer hash (`:973`); numeric coverage corrections too (`:1251`). Because the
   answer changes on every draft, the *same* complaint gets a *new* ID on the next draft
   and the old one remains an open obligation.
2. **A fresh reading can mint fresh assertions.** The schema requires at least one
   assertion per finding (`:283`) and permits up to 64, each with a 300-character reason
   (`:284-290`). Nothing requires the reviewer to re-use the assertion set from the
   previous draft, so a repaired finding can legitimately produce a new
   `insufficient_evidence` judgment - and that creates a new mandatory correction
   (`:1229-1235`).
3. **No dedupe, no cap on new work.** New corrections are accepted up to 32 per pass
   (`:294`, `:821-824`); code-added corrections have no cap at all. The prompt asks for
   `related_correction_id` to avoid copies (`:1149`), but code only validates that a
   *declared* refinement carries a matching judgment (`:1182-1186`). An undeclared
   duplicate is accepted.
4. **The queue can make the review impossible.** At more than 64 obligations,
   `correction_judgment_schema` raises and the support phase cannot run at all
   (`:767-770`).

The support-phase counts in run 35 rose 4 -> 9 -> 11 across three drafts, while
completeness went 1 -> 2 -> 0 -> 4. These are two different queues and neither is monotone,
so the numbers show new obligations outrunning retirement, not an arithmetic runaway. Run
36's support counts were 6 -> 2 -> 5 and did not reproduce the growth. The structural
argument rests on mechanisms 1 and 2 in code, not on this sample.

## 1.5 What the verdict forces

`must_revise` (`:1270-1272`) is set if there is any deterministic issue, any issue at all,
any withheld finding, an accuracy or safety rating below 3, or any 1-rated dimension. So
conservative review always produces `revise`, and `revise` must carry at least one
correction or the submission is rejected and retried (`:1274-1277`). A reviewer that
rates accuracy 2 without listing a correction therefore loses a model call to a
guaranteed rejection.

## 1.6 Budget behavior under pressure

- Three attempts per phase (`:1135`).
- A provider `RuntimeError` (including `output_token_limit`) is **not** retried: it fails
  the phase immediately (`:1152-1155`). Run 35 died on attempt 1 at 6,000 output tokens
  with 5,999 reasoning tokens.
- Each attempt resends the full payload (evidence, all findings, all obligations,
  instructions), so a rejection costs a full-price call. The only reduction after a
  rejection is dropping already-retained finding schemas (`:1203-1207`).

# Part 2 - How Original delivers the answer

## 2.1 The draft loop

`MAX_DRAFTS = 4` (`original.py:22`), loop at `:592-790`. Per draft: coordinate, validate
the evidence handoff, optionally plan a chart, review, then accept or repair. A new
`ZeroSugarAgent` is constructed per draft (`:634-638`), so review state does not carry
over except the explicit `pending_corrections`.

## 2.2 The 21-versus-12 loop (run 36, reproducible from code)

The delivery tool is described as "Submit additions and explicit edits to the saved
answer" (`runtime.py:284-299`). What actually happens:

1. The model submits `interpretations` (schema cap 12, `grounding.py:198`).
2. `resolve_answer` keeps the current draft's blocks, removes `remove_ids`, appends the
   submitted additions, and dedupes identical items (`content.py:153-179`).
3. `render_answer` validates the **merged** payload, where the same 12-item cap applies
   (`grounding.py:304-306`).

So a model that resubmits the full list, or adds without removing, produces
`len(retained) + len(new) - duplicates`. Run 36 recorded **seven** rejections, one per turn
from turn 1 to turn 7: 21, 25, 24, 23, 23, 23, 23 against a limit of 12.

Three defects compound here:

- The field is documented as *additions*, but its content and the schema cap read as *the
  list*. The schema caps additions at 12 (`content.py:183-205`) regardless of how many
  blocks are retained, while the merged list is also capped at 12.
- The rejection does report `expected_count: 12` and `actual_count: 21`, so the size is
  communicated. What it does not report is the retained count or which `block_id`s to
  remove - and it cannot, because `remove_ids` is only applied after the call resolves.
- After the first rejection the runtime replaces the correction with a hardcoded
  fact/citation paragraph (`runtime.py:395-398`) that says nothing about narrative counts.
  The submitted counts fell 25 -> 23 and then stayed at 23 for four turns. Explicit
  numbers were not enough, and nothing forced a different action before the turn cap.

## 2.3 The repair prompt is the whole previous verdict

On `revise`, the repair context is the complete serialized verdict plus evidence
(`original.py:782-790`): every finding, every assertion, every reason, every correction,
plus the source packet. That is why Original-turn inputs reached 37-45k tokens in run 35.
The model is asked to re-derive its answer from a document that is mostly review
commentary about the previous answer.

## 2.4 The challenge path adds, it does not subtract

`challenge_corrections` (`original.py:301-351`) runs a full extra support review of the
same candidate, bounded to once per candidate (`:314`) and eight correction IDs. Its
verdict replaces `last_verdict` and its corrections become the next `pending_corrections`
(`:687-688`). A challenge can therefore grow the queue as easily as shrink it, at the cost
of one complete review call.

## 2.5 Failure handling is honest but coarse

`_execute_workflow` catches everything and returns `partial` or `failed`
(`original.py:489-505`). The stage is recorded, and partial release with a reviewed older
candidate is preserved (`:507-555`). What is missing is a closed failure taxonomy: a
turn-limit storm, a truncation, a schema loop and a real analysis gap all land in the same
`failed`/`partial` bucket.

# Part 3 - Findings

## P0-1 The answer-delivery loop cannot converge
`runtime.py:284-299`, `content.py:137-180,183-205`, `grounding.py:198-205,304-306`.
The additions schema allows up to 12 new narrative items regardless of how many blocks are
already retained, while the renderer enforces 12 on the merged list. Observable: six
identical rejections then turn exhaustion (run 36). The model is shown the current draft
with block IDs, so it can count retained blocks, and the rejection reports 12 against
21-25. What it is not told is how many are retained or which to remove, and a static
schema cap cannot reconcile with a 12-item merged cap while `remove_ids` is applied after
the call.

## P0-2 The obligation queue cannot converge
`zero_sugar.py:1211,1217-1235,1248-1251,1261-1269,767-770`.
Candidate-hashed identities, fresh assertions every draft, no merge and no cap. Run 35's
support phase counted 4, 9 and 11 issues across three drafts; run 36 counted 6, 2 and 5, so
growth is observed once and is not general. What is general is the mechanism: a new answer
hash re-keys the same complaint, so retirement never reduces the queue reliably.

## P0-3 The review does not fit the output budget
`zero_sugar.py:283-290,294-302,1110-1131`; the per-profile `max_output_tokens` (6,000 for
the APInex profiles in `connections.json`) is shared with reasoning. A single call must
rate 7 dimensions, judge 13-16 findings with assertions, judge every obligation and list
new corrections, within 6,000 tokens of which ~99% went to hidden reasoning on the failing
attempt.

## P0-4 There is no verification gate
91/329 red, 78 of them from the uncommitted change, and live runs continued. Triaging the
two failures revision 1 called production defects: `agent_snapshot` reads `.reader` only
under `name == 'Cherry'`, and a real Cherry always sets it (`cherry.py:62-64`), so that is
a test double. `database_identity` raising on a missing path is correct for resume
(`resume.py:200`); the real defect is `plan()` hashing the database eagerly in every mode
(`original.py:111-113`), which makes offline unit tests require a database file.

## P1-5 Truncation aborts instead of degrading
`zero_sugar.py:1152-1155`. A token-limit error fails the phase on attempt 1; there is no
smaller re-ask, no batching, no partial verdict.

## P1-6 Retries are not informative or escalating
`runtime.py:392-401`, `zero_sugar.py:884-888`. Rejections do carry `expected_count` and
`actual_count`, so the size is communicated. What is missing is the retained count and the
removable block IDs, and the recurrence branch (`runtime.py:395-398`) replaces the
correction with a hardcoded fact/citation paragraph that is irrelevant to a narrative
count.

## P1-7 Schema compliance consumes the workflow
Run 36: 26 model calls, 11 `structured_response_repair` events, two wasted on free-form
output. The per-candidate schema is rebuilt with a keyed object per finding
(`zero_sugar.py:336-356`), and every field is a rejection path.

## P1-8 Failure classification is too coarse
`original.py:489-505`, `zero_sugar.py:1307-1314`. `invalid_review` covers at least five
causes; `execution_error` covered a bare `KeyError` in runs 33-34.

## P1-9 The suite cannot act as a gate
Prompt-text coupling (`tests/test_sentiment_workflow_repairs.py:44` splits a prompt
string), mock-only coverage, no test for `agents/content.py`, and 13 pre-existing errors.

## P1-10 Change and evaluation hygiene
21 uncommitted files across 9 modules and 12 documents, no branch, no bisect path; and the
20 live runs vary question, model and code together while the fixed cases in
`tests/evaluation_cases.json` are unused.

## P2-11 Documentation outruns evidence
331 KB of markdown against 423 KB of Python, with stale test counts and several
"unvalidated" markers. Documentation is standing in for a green suite and a metrics table.

## P2-12 Captured data has no retention policy
34.8 MB of full exchanges with employee comment text, unencrypted, git-ignored but not
otherwise controlled.

# Part 7 - Limits of this audit

- The suite was run twice (working tree 235 s, HEAD worktree 213 s). No model calls were
  made and no code was changed.
- Revision 2 exists because revision 1 was wrong in four places. An external reader
  proposed keeping the additions contract, treating the two `capture.py` crashes as test
  doubles, not keying obligations on text or `finding_id`, and not fixing assertion counts
  by decree. Each was checked against code above and accepted. An audit gets the same
  review it asks of the code.
- Revision 3 exists because revision 2 was wrong in three places and imprecise in three
  more. The static addition cap, the claim-only identity and the owner-only delegation were
  each unusable as written; the rejection count, the feedback contents and the mixed
  obligation series were each wrong in the text. All six claims were re-checked against
  `reports/logs/20261028_182436_7880786d891c.jsonl` and
  `reports/logs/20261028_181720_d4ee97db2de5.jsonl` rather than against the previous
  summary.
- Loop mechanisms are read from code and confirmed against two runs (35, 36). They are
  deterministic in construction, but I have not replayed them with a scripted model; that
  replay is part of the acceptance criteria above.
- A red test may be a stale expectation or a real defect. This audit establishes that the
  suite cannot be trusted as a gate, not which side each test falls on.
- Thirteen supported findings are not thirteen correct findings. Model acceptance is not
  independent human validation.
- The UI section describes the current artifact surface as read from `Echo_UI/backend`
  imports; it is not a UI review and makes no claim about UI behavior.
